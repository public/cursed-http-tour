cursed-http · a guided tour

Trying to serve 500,000 people from a $12 computer by doing everything the hard way

A walkthrough, for curious non-experts, of a web server built for a speed contest. It uses every trick its authors could justify, and a few they mostly built because they could.

The game

One small box, as many users as it can carry

The $12 server challenge asks everyone to build the same tiny social network: a feed of posts, the ability to read one post, like it, and write a new one, with logins checked on every write. Everyone gets the same cheap rented machine.

Then the organizer points a crowd of simulated users at it. Each one scrolls the feed, opens a post, sometimes likes it, rarely writes one, and pauses to "read" in between. The crowd grows until the server cracks. Your score is the largest crowd the server holds for five minutes while three things stay true:

  • 95% of requests answered in under half a second,
  • 99% answered in under one second,
  • fewer than 1% of requests fail.

That's the only number that counts. Not elegance, not requests per second. Every decision on this page was judged by one question: does it let us hold more users?

In plain termsEach user only asks for something about once every 24 seconds, so the goal of 500,000 users is about 21,000 requests a second. One core has to deal with each in roughly 47 millionths of a second (µs), on average, forever.

Where the time actually goes

You might guess the hard part is the "thinking": reading the request, checking the login, querying the database. Measured on the real Xeon, it mostly isn't. Most of each request's time is the operating system shuffling network packets.

So why make parsing 3× faster, if it was never the bottleneck? Partly because the project's brief was "maximally cursed", and partly because each nanosecond saved is free. The real wins, though, come from the parts that move the big bar: how the server talks to the kernel, how it touches the database, and how much memory each user costs. Memory turns out to be the wall that matters most.

The journey of a request

Follow one request through the server

The server is one program running on one thread. It never handles requests one at a time. Every time it wakes up, it grabs everything that has arrived (up to 128 requests or 2 ms of waiting) and pushes the whole batch through five stages together.

1RECEIVE

Talking to the kernel without knocking on its door

A program can't touch the network card itself. It has to ask the operating system's kernel: "anything new on connection 4,071?", "please send these bytes". Each ask is a system call. That's a trip across a security boundary, and it costs far more than ordinary code. With 300,000 connections, a classic server makes millions of those trips a second.

io_uring is a newer Linux feature that replaces the knocking with two shared mailboxes. The program drops requests into one ring ("receive on all of these", "send this"), and the kernel drops finished results into the other. One system call can hand over hundreds of jobs, and sometimes none is needed at all.

The 65,535 problem, and the multi-ring trick

The contest machine limits each program to 65,535 open files, and on Linux every network connection normally counts as a file. That would cap the server at about 65,000 users, far short of the 500,000 goal.

io_uring has an escape hatch called direct descriptors: connections that live only inside a ring's private table and never become ordinary files. Each ring's table also tops out at 65,535, so the server simply runs several rings and adds another whenever the current ones fill up. Here's the code that asks the kernel to accept a new connection straight into a free slot of a ring's table:

explore/io/loop.craw io_uring, no helper library
static void arm_accept(loop_t *L, int ri, int multi)
{
    ring_t *r = &L->rings[ri];
    struct io_uring_sqe *s = get_sqe(L, r);      // a free slot in the submission ring
    s->opcode = IORING_OP_ACCEPT;
    s->fd = L->lfd;                              // the listening socket
    s->ioprio = multi ? IORING_ACCEPT_MULTISHOT : 0;
    s->file_index = IORING_FILE_INDEX_ALLOC;     // "put it in your own table, not in the file table"
    s->user_data = ud_mk(OP_ACCEPT, (unsigned)ri, multi ? 0 : 1, 0);
    if (multi) { r->accepting = 1; L->acc_ring = ri; }
    else r->singles++;
}

Receiving is tuned for memory, not just speed. Most connections sit idle most of the time, so each idle one holds only a cheap standing "tell me when data arrives" ticket (a multishot poll), rather than a parked receive. That saves about 190 bytes per connection on this kernel, and 608 on newer ones. When data shows up, a single receive pulls it into a shared pool of buffers. This mode had a bug the local arena caught at 400,000 users: when a huge crowd of connections closed at the same moment, their memory lingered for about a second, and the server ran out. It's fixed (a 60,000-connection mass-close test now leaves nothing behind), and a re-run at 400,000 is pending. The server also keeps 256 accepts in flight, because on this kernel version the fancier "accept forever" mode stalls under a flood of new connections. Lessons like that came from reading rival entries.

2PARSE

Reading 64 letters in one step

A request arrives as plain text: a line like GET /posts/42 HTTP/1.1, then a few header lines such as Authorization: Bearer …, each ending in an invisible line-break. The usual way to read it is letter by letter: is this a line-break? no. This one? no…

Modern CPUs have SIMD instructions (Single Instruction, Multiple Data). One instruction loads 32 or 64 letters into a wide register and compares all of them against a line-break at once. The answer comes back as a bitmask, one bit per letter, with a 1 wherever there's a match. Finding the next line is then just "where's the next 1 bit?", which is itself a single instruction.

Try it: the line-break mask

Edit the request. Each box is one byte of the first 64. The highlighted ones are the line-breaks (\n) that a single compare finds in one go.

Here's the real version for Intel's AVX2 instructions. It loads two 32-byte chunks, compares every byte against '\n', and squeezes the results into one 64-bit mask, exactly like the demo above:

explore/parser/http.halso has AVX-512, ARM NEON and plain-C versions
FP_INLINE uint64_t fp_lf64_simd(const char *p) {
  const __m256i LF = _mm256_set1_epi8('\n');                     // 32 copies of '\n'
  __m256i v0 = _mm256_loadu_si256((const void *)p),               // bytes 0..31
          v1 = _mm256_loadu_si256((const void *)(p + 32));        // bytes 32..63
  return fp_mm2(_mm256_cmpeq_epi8(v0, LF), _mm256_cmpeq_epi8(v1, LF));   // 64 compares -> 64 bits
}

There's a second twist: the parser isn't hand-written. A script generates it from the API's own specification, so it knows the handful of request shapes this API can receive and recognises each from its first few bytes. Anything unusual (an old HTTP version, odd headers) falls back to a slower general-purpose parser. That one is SIMD too, and it gives identical answers to the well-known picohttpparser on every input the team could throw at it.

Result on the Xeon: 37 nanoseconds per request, against 107 for picohttpparser with the same routing on top.

The really cursed bit: parsing different people's requests side by side

SIMD normally speeds up one long piece of text. But each request is short, and a batch holds dozens of them from different users. So the "lane-parallel" parser turns the problem sideways: it puts one request from each of 4 or 8 connections into the lanes of a single register, and parses them all with the same instructions.

explore/batch-parse/bp.hthe whole contract in two lines
const char *buf[n]; int len[n];  req_t out[n]; int ret[n];
bp_parse(n, buf, len, out, ret);    // ret[i] = fast_parse(buf[i], len[i], &out[i]), any n >= 0

Every lane must return exactly what the one-at-a-time parser returns. A test build checks that live: 165,004 real requests compared lane by lane, with zero mismatches.

3LOG-IN CHECK

Checking eight signatures with one set of instructions

Liking a post or writing one requires a login token, a JWT. It's a short string that says "this is user 1234, valid until Tuesday", followed by a cryptographic signature. To check it, the server recomputes the signature with a secret key (a calculation called HMAC-SHA256) and compares. The rules forbid caching the answer: every request's token is checked from scratch.

SHA-256 is 64 rounds of adding, rotating and mixing 32-bit numbers. One message can't be split across lanes, because each round needs the previous one. But eight different messages can each take a lane. That's multi-buffer hashing: the server gathers every token in the batch and runs them through the rounds side by side, one token per 32-bit lane of an AVX-512 register.

Below is one SHA-256 round. V is "a vector of 8 numbers", so every VADD or VROR is one instruction doing eight lanes' worth of work. The identical source becomes the plain-C version when V is just a single number.

explore/jwt/jwt_mb.incone round, for every lane at once
#define MB_RND(a, b, c, d, e, f, g, h, t, wt)                                    \
    do {                                                                         \
        V t1 = VADD(VADD(VADD(h, VXOR3(VROR(e, 6), VROR(e, 11), VROR(e, 25))),   \
                         VADD(VCH(e, f, g), VSET1(K256[t]))), (wt));             \
        V t2 = VADD(VXOR3(VROR(a, 2), VROR(a, 13), VROR(a, 22)), VMAJ(a, b, c)); \
        d = VADD(d, t1);                                                         \
        h = VADD(t1, t2);                                                        \
    } while (0)

A practical detail: this Xeon slows its clock when code uses the full 512-bit registers heavily, so the shipped version uses AVX-512's new instructions on 256-bit registers instead. The 512-bit variant was measured, and rejected.

On the Xeon, with a typical batch of three tokens: 608 ns per token, against 6,201 ns for the C++ library jwt-cpp and 8,739 ns for Go's popular golang-jwt.

4DATABASE

Skipping SQL and operating on SQLite directly

The contest requires the data to live in SQLite, the small database inside most phones and browsers. Normally you hand SQLite a sentence in the SQL language. SQLite parses it, plans how to run it, compiles it into its own little bytecode, and runs that on its storage engine, a B-tree: a sorted tree of 4 KB pages where finding any row takes only a few hops from the top.

This server skips most of that. The "feed" and "get a post" reads are compiled into the same program as SQLite itself, and they call SQLite's internal B-tree functions directly.

For example, a feed needs the like count of 20 posts. Instead of 20 separate counting queries, the engine positions one cursor at the lowest post id in the "likes by post" index and walks forward once, tallying as it goes:

explore/db/engine.ctrimmed: the fast cell-walking variant is left out
// Counts likes for post ids in [lo, hi] with one likes_post_id_idx range scan.

  BtCursor *c = rcur(e, C_L); if (!c) return -1;
  UnpackedRecord *r = e->uk_lpid; int res;
  r->nField = 1; r->default_rc = +1; r->eqSeen = 0; r->errCode = 0;
  r->aMem[0].flags = MEM_Int; r->aMem[0].u.i = lo;            // search key: post id lo
  if (sqlite3BtreeIndexMoveto(c, r, &res) != SQLITE_OK) return -1;
  ...
  do {
    u32 amt; const u8 *rec = idx_fetch(c, &amt); u64 t[1]; const u8 *d[1];
    if (!rec || rec_decode(rec, amt, 1, t, d) != 1 || !st_isint(t[0])) return -1;
    i64 pid = st_int(t[0], d[0]);
    if (pid > hi) break;                                          // past the last post: done
    total++; if (counts) counts[pid - lo]++;
  } while ((rc = sqlite3BtreeNext(c, 0)) == SQLITE_OK);
  return rc == SQLITE_OK || rc == SQLITE_DONE ? total : -1;
}

Then: patching SQLite itself

The team tried changes inside SQLite's own source and kept only the three that won on the real Xeon. Each leaves the file format, the query results and the bytes written to disk identical to stock SQLite. One example: when you look up row 1,209 right after row 1,208, they're almost certainly on the same leaf page, yet stock SQLite climbs back to the root of the tree every time. The btree-sameleaf patch checks the leaf first.

explore/sqlite-patches/patches/btree-sameleaf.patchthe core of a 46-line patch to sqlite3.c
+  /* If the cursor is on a leaf whose rowids span intKey, the row (if any)
+  ** is on this leaf: search it without going back to the root. */
+  if( pCur->eState==CURSOR_VALID
+   && pCur->iPage>0
+   && pCur->pPage->leaf
+   && pCur->pPage->isInit
+   && pCur->pPage->nCell>1
+  ){
       ...  compare intKey with the first and last cell's rowid  ...
+        goto moveto_table_search_page;
+  }
   rc = moveToRoot(pCur);

The other two: btree-interp searches a page the way you'd look up a word in a dictionary (row 1,209 on a page of rows 1,101–1,250 is probably about 70% of the way in), rather than always halving. pcache1-maxkey removes a needless scan of SQLite's page cache at every commit. Not every idea survived: putting SIMD inside SQLite's page search lost on the Xeon, so it was dropped.

Saving writes: one disk write per commit

SQLite in "WAL" mode appends each changed page to a log file. It writes each page as two pieces, a 24-byte header and then the 4 KB page, so a commit that touches 10 pages makes 20 separate write calls. The server slips a thin layer between SQLite and the disk that holds the pieces in memory and sends the whole commit as one write. It knows the commit is complete because SQLite marks the last frame's header.

explore/db/engine.cthe end of the shim's write function
  memcpy(c->buf + c->n, b, (size_t)n); c->n += (size_t)n;     // just remember the bytes
  if (n == 24) {                                                 // a 24-byte frame header:
    const u8 *h = b;                                             //   non-zero "db size" = commit frame
    c->commit_hdr = (h[4] | h[5] | h[6] | h[7]) != 0;
    return SQLITE_OK;
  }
  if (c->commit_hdr) { c->commit_hdr = 0; return cw_flush(c); }   // the commit frame is complete
  return SQLITE_OK;

The checkpoint write gate

The log file can't grow forever. Every so often SQLite copies the logged pages back into the main database file, a checkpoint, and then waits for the disk to confirm. On the test box that wait takes 130–270 ms, and if it happens in the middle of serving, every request in line waits too. That spike was the single biggest threat to the "99% under 1 second" rule.

The fix is a second thread that checkpoints in the background, plus a gate. When the log reaches its high mark, the server keeps answering reads but leaves new writes waiting, unread, in the network buffers until the checkpoint catches up (typically about 55 ms). Then they're processed normally.

explore/db/engine.casked once per batch: should POSTs wait?
int eng_writes_paused(eng *e) {
  if (!e->drain) return 0;
  u32 mx, pend; wal_state(e, &mx, &pend);
  double held = mono_ms() - e->drain_t0;
  if (pend == 0 || held > e->o.ckpt_drain_ms) {          // caught up, or give up waiting
    __atomic_store_n(&e->drain, 0, __ATOMIC_RELEASE);
    ...
    return 0;
  }
  return 1;                                             // keep holding writes
}

The checkpoint also had a memory cost. The kernel kept the whole log file cached in memory (up to ~256 MB), and that's memory the connections need. The final version checkpoints in smaller passes and tells the kernel to forget each log page once it has been copied back (posix_fadvise). That cut the log's cached memory to 15–18 MB on the Xeon (experiments 39 and 40). Testing also caught a real bug along the way: under write-heavy load the gate never closed, so the log just kept growing. It's fixed.

One more batch-level trick is allowed outright by the rules: group commit. All of a batch's writes share one transaction and one commit, and every reply in the batch waits for it.

5REPLY

The memory wall, and hanging up on purpose

Replies are assembled in a per-batch scratch area and handed to the kernel only after the commit. The interesting decision is a single header: whether the reply says Connection: close.

Remember the first chart: CPU isn't the scarce thing. At this scale, memory is. Every open connection costs the kernel about 4.3 KB, measured on the Xeon, and that can't be shrunk without admin rights. The box has about 1,630 MB free. After leaving room for the server itself and its database cache, it runs out somewhere around 340,000 idle connections. That's well short of the 500,000-user goal, so keeping one connection per user can't get there.

The way past the wall comes from reading the organizer's load generator. Simulated users spend most of their time "reading", time spent reconnecting isn't counted as delay, and a user whose connection was closed simply opens a new one next time. So near the memory limit, the server attaches Connection: close to a fraction of replies. Idle users then share fewer open connections, and the server can carry more users than it has sockets.

Play with it: users vs. the memory wall

A rough model: 4.3 KB of kernel memory per open connection, against the ~1,430 MB left of the box's 1,630 MB once about 200 MB is set aside for the server and its database cache. With shedding, the small Xeon test settled at 2.75 users per open connection. That test used 5,000 users, so treat the shedding line as an illustration.

Everyone keeps a connection open
With "Connection: close" shedding

Hanging up isn't free. Each reconnect costs the server about 8–9 µs of extra CPU on the Xeon (experiment 18), but there's CPU to spare at the wall. Shedding only kicks in near the memory-derived cap, it never interrupts a request in progress, and it applies to everyone alike. In the Xeon test it caused zero errors in 129,730 requests (experiment 6). The decision itself is a coin flip weighted by how close to the wall the server is:

explore/io/loop.cclose_frac rises as free memory falls
int loop_close_hint(loop_t *L, loop_conn id)
{
    (void)id;                                   // never aimed at a particular client
    float f = L->st.close_frac;
    if (f <= 0) return 0;                       // plenty of memory: keep everyone
    L->rng ^= L->rng << 13; L->rng ^= L->rng >> 17; L->rng ^= L->rng << 5;   // xorshift
    if ((float)(L->rng >> 8) < f * 16777216.0f) { L->st.hint_closes++; return 1; }
    return 0;
}

The server's own memory is small next to the kernel's: 32 bytes per connection in the program itself, against 63 for the previous leader, measured side by side on the Xeon with 60,000 idle connections (experiment 37). That works out to roughly 100 MB less at 340,000 connections, room for about 23,000 more. In the local load-test arena at 50,000 users, where both servers passed, the whole server peaked at 229 MB against the leader's 255 MB, That's laptop Docker, not the Xeon, but it's the same direction. Below the normal shedding policy there are emergency floors as a last resort: under 100 MB free it stops accepting new connections, and under 60 MB it gently closes connections that have been idle for 20 seconds. That beats letting the system's out-of-memory killer end every connection at once.

The memory accounting itself was a small investigation. The usual "free memory" figure turned out to overstate headroom by about 1 KB per connection, because some kernel memory looks reclaimable but stays pinned while the socket is open. The server now measures available memory minus that "reclaimable" slice, and sets its cap from that.

★BEHIND THE SCENES

A queue for the one machine whose opinion counts

All of this was written on an Apple laptop, a different kind of chip entirely. It can't run AVX-512 at all, and it turned out to be misleading in both directions: SQLite paths ran 2.7–4× slower on the Xeon, and the laptop's fast disk hid the checkpoint stall completely. So the rule became: only the Xeon decides.

The team rented two machines matching the contest box (same Xeon Platinum 8260, same 1 core and 2 GB, same Linux kernel). About fifteen AI coding sessions were working on different parts in parallel, but none of them logs in to the boxes. Instead, one session acts as a broker:

{"requester_session_id": "local_…",

 "reasoning": "measures batch p99 with the gate vs inline checkpoints; decides the checkpoint design, which sets the tail latency that fails runs",
 "timeout_s": 180, "needs_root": false}

The broker also ran known entries, a C++ server and the previous contest leader (written in Rust), on the same boxes as rulers. That's how the team knows how its numbers relate to the organizer's machine. Under the same load, this server used 32.2 µs of CPU per request against the leader's 37.6 µs.

Every trick has an off switch

How cursed would you like it?

Each unusual thing the server does can be switched off when it's built, one knob at a time, or all at once with CURSED=boring. The boring build is by-the-book: stock SQLite, ordinary SQL queries, SQLite's own file layer and checkpoints, plain one-at-a-time login checks, and the standard picohttpparser for every request. Both builds pass the contest's 42 checks, so you can measure exactly what each trick buys.

The fallback parser is swappable too: our SIMD one, picohttpparser, Node's llhttp, uWebSockets (C++), hparse (Zig) or httparse (Rust). All 24 combinations of fast and fallback parser pass the 42 checks. With every SQLite knob combined, 52 database configurations pass with the database's integrity check clean (Linux, in Docker). The server prints the mode it was built with when it starts.

The boring build doesn't just promise to stay on SQLite's public API; it's checked. The build lists every SQLite function the program references and fails if any of them isn't in SQLite's public header. The public-API engine and the cursed one gave byte-identical responses to 3,408 test requests.

Pocket glossary

µs / ns
Microsecond (a millionth of a second) / nanosecond (a billionth).
p95, p99
The response time that 95% (or 99%) of requests beat. The contest cares about the slow tail, not the average.
kernel
The core of the operating system. It owns the network card, the disk and memory, and programs must ask it for everything.
system call
One request from a program to the kernel. Relatively expensive.
io_uring
A Linux interface where program and kernel exchange work through shared queues instead of one call per operation.
SIMD
CPU instructions that apply one operation to many values at once (AVX2: 32 bytes, AVX-512: 64 bytes).
JWT, HMAC
A signed login token, and the keyed hash used to check its signature.
B-tree
The sorted tree of pages SQLite stores tables and indexes in.
WAL, checkpoint
SQLite's append-only change log, and the step that copies it back into the main file.
