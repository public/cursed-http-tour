cursed-http · a guided tour

Serving a crowd from a $12 computer by doing everything the hard way

A walkthrough, for curious non-experts, of a web server built for a speed contest. It uses every trick its authors could justify, and a few they mostly built because they could.

The entry itself: pull request #158 on the challenge repo. This page describes the build at its head, commit 2b66022.

The game

One small box, as many users as it can carry

The $12 server challenge asks everyone to build the same tiny social network: a feed of posts, the ability to read one post, like it, and write a new one, with logins checked on every write. Everyone gets the same cheap rented machine.

Then the organizer points a crowd of simulated users at it. Each one scrolls the feed, opens a post, sometimes likes it, rarely writes one, and pauses to "read" in between. The crowd grows until the server cracks. Your score is the largest crowd the server holds for five minutes while three things stay true:

  • 95% of requests answered in under half a second,
  • 99% answered in under one second,
  • fewer than 1% of requests fail.

That's the only number that counts. Every decision on this page was judged by one question: does it let us hold more users?

In plain termsEach simulated user asks for something about once every 10 seconds. The previous winner held 264,000 users, which is about 25,000 requests a second. One core has to deal with each in roughly 40 millionths of a second (µs), on average, forever.

Two things run out: CPU time and memory. Of the roughly 30 µs this server spends per request on the Xeon, most is the kernel's own network work (about 13 µs on the Xeon, 6 µs locally), which no change to the server's code can remove. So the tricks below go after everything else: how the server talks to the kernel, how it touches the database, and how much memory each user costs. Parsing and login checks were never the bottleneck; making them fast anyway is where the "cursed" comes in.

The journey of a request

Follow one request through the server

The server is one program running on one thread. It never handles requests one at a time. Every time it wakes up, it grabs everything that has arrived (up to 128 requests or 2 ms of waiting) and pushes the whole batch through five stages together.

1RECEIVE

Talking to the kernel without knocking on its door

A program can't touch the network card itself. It has to ask the operating system's kernel: "anything new on connection 4,071?", "please send these bytes". Each ask is a system call, a trip across a security boundary that costs far more than ordinary code. With 300,000 connections, a classic server makes millions of those trips a second.

io_uring is a newer Linux feature that replaces the knocking with two shared mailboxes. The program drops requests into one ring ("receive on all of these", "send this"), and the kernel drops finished results into the other. One system call can hand over hundreds of jobs. The server uses raw io_uring system calls, with no helper library, and falls back to ordinary epoll where io_uring isn't available.

The 65,535 problem, and the multi-ring trick

The contest machine limits each program to 65,535 open files, and on Linux every network connection normally counts as a file. That would cap the server at about 65,000 users.

io_uring has an escape hatch called direct descriptors: connections that live only inside a ring's private table and never become ordinary files. Each ring's table also tops out at 65,535, so the server runs several rings and adds another whenever the current ones fill up. Here's the code that asks the kernel to accept a new connection straight into a free slot of a ring's table:

explore/io/loop.craw io_uring, no helper library
static void arm_accept(loop_t *L, int ri, int multi)
{
    ring_t *r = &L->rings[ri];
    struct io_uring_sqe *s = get_sqe(L, r);      // a free slot in the submission ring
    s->opcode = IORING_OP_ACCEPT;
    s->fd = L->lfd;                              // the listening socket
    s->ioprio = multi ? IORING_ACCEPT_MULTISHOT : 0;
    s->file_index = IORING_FILE_INDEX_ALLOC;     // "put it in your own table, not in the file table"
    s->user_data = ud_mk(OP_ACCEPT, (unsigned)ri, multi ? 0 : 1, 0);
    if (multi) { r->accepting = 1; L->acc_ring = ri; }
    else r->singles++;
}

Each connection keeps one standing ("multishot") receive armed, so the kernel drops every new request into a shared pool of buffers without being asked again. (A leaner mode that holds only a cheap poll per idle connection saves about 190 bytes each, but left about 631 MB of socket buffers behind when 300,000 connections closed at once, so it's opt-in.) The server keeps 256 single accepts in flight, because on this kernel the "accept forever" mode stalls under a flood of new connections.

Drain-first: waiting in our memory, not the kernel's

A request that arrives while the server is busy would normally wait in the kernel's socket buffer, at about 4 KB of kernel memory per request. Instead the server copies each request out as soon as it arrives, into its own compact buffers at about 0.5 KB each, and works through them in order. Parsing, login checks, commit-before-reply and per-connection order are unchanged; only where the waiting happens moves. On the Xeon it costs no measurable CPU at normal load and cuts median latency by about 30%. Its real job is in the memory wall.

2PARSE

Reading 64 letters in one step

A request arrives as plain text: a line like GET /posts/42 HTTP/1.1, then a few header lines such as Authorization: Bearer …, each ending in an invisible line-break. The usual way to read it is letter by letter: is this a line-break? no. This one? no…

Modern CPUs have SIMD instructions (Single Instruction, Multiple Data). One instruction loads 32 or 64 letters into a wide register and compares all of them against a line-break at once. The answer comes back as a bitmask, one bit per letter, with a 1 wherever there's a match. Finding the next line is then "where's the next 1 bit?", which is itself a single instruction.

Try it: the line-break mask

Edit the request. Each box is one byte of the first 64. The highlighted ones are the line-breaks (\n) that a single compare finds in one go.

Here's the real version for Intel's AVX2 instructions. It loads two 32-byte chunks, compares every byte against '\n', and squeezes the results into one 64-bit mask, exactly like the demo above:

explore/parser/http.halso has AVX-512, ARM NEON and plain-C versions
FP_INLINE uint64_t fp_lf64_simd(const char *p) {
  const __m256i LF = _mm256_set1_epi8('\n');                     // 32 copies of '\n'
  __m256i v0 = _mm256_loadu_si256((const void *)p),               // bytes 0..31
          v1 = _mm256_loadu_si256((const void *)(p + 32));        // bytes 32..63
  return fp_mm2(_mm256_cmpeq_epi8(v0, LF), _mm256_cmpeq_epi8(v1, LF));   // 64 compares -> 64 bits
}

The parser isn't hand-written: a script generates it from the API's own specification, so it knows the handful of request shapes this API can receive and recognises each from its first few bytes. Anything unusual falls back to a general parser that is SIMD too and gives identical answers to the well-known picohttpparser on every input tested. Result on the Xeon: 37 nanoseconds per request, against 107 for picohttpparser with the same routing on top. The parser now lives in its own MIT-licensed library, cursed-http-parser, which the server vendors at a pinned commit that its build script checks.

The really cursed bit: parsing different people's requests side by side

Each request is short, but a batch holds dozens of them from different users. So the "lane-parallel" parser turns the problem sideways: it puts one request from each of 4 or 8 connections into the lanes of a single register, and parses them all with the same instructions.

explore/batch-parse/bp.hthe whole contract in two lines
const char *buf[n]; int len[n];  req_t out[n]; int ret[n];
bp_parse(n, buf, len, out, ret);    // ret[i] = fast_parse(buf[i], len[i], &out[i]), any n >= 0

Every lane must return exactly what the one-at-a-time parser returns. A test build checks that live: 165,004 real requests compared lane by lane, with zero mismatches.

3LOG-IN CHECK

Checking eight signatures with one set of instructions

Liking a post or writing one requires a login token, a JWT: a short string that says "this is user 1234, valid until Tuesday", followed by a cryptographic signature. To check it, the server recomputes the signature with a secret key (HMAC-SHA256) and compares. The rules forbid caching the answer: every request's token is checked from scratch.

SHA-256 is 64 rounds of adding, rotating and mixing 32-bit numbers. One message can't be split across lanes, because each round needs the previous one. But eight different messages can each take a lane. That's multi-buffer hashing: the server gathers every token in the batch and runs them through the rounds side by side, one token per 32-bit lane of an AVX-512 register.

Below is one SHA-256 round. V is "a vector of 8 numbers", so every VADD or VROR is one instruction doing eight lanes' worth of work. The identical source becomes the plain-C version when V is just a single number.

explore/jwt/jwt_mb.incone round, for every lane at once
#define MB_RND(a, b, c, d, e, f, g, h, t, wt)                                    \
    do {                                                                         \
        V t1 = VADD(VADD(VADD(h, VXOR3(VROR(e, 6), VROR(e, 11), VROR(e, 25))),   \
                         VADD(VCH(e, f, g), VSET1(K256[t]))), (wt));             \
        V t2 = VADD(VXOR3(VROR(a, 2), VROR(a, 13), VROR(a, 22)), VMAJ(a, b, c)); \
        d = VADD(d, t1);                                                         \
        h = VADD(t1, t2);                                                        \
    } while (0)

This Xeon slows its clock when code leans on the full 512-bit registers, so the shipped version uses AVX-512's new instructions on 256-bit registers. The verifier is its own MIT library too, cursed-jwt, and it picks the fastest version the CPU supports when the server starts: on the Xeon that's the AVX-512 one. On the Xeon, with a typical batch of three tokens: 608 ns per token, against 6,201 ns for the C++ library jwt-cpp and 8,739 ns for Go's golang-jwt.

4DATABASE

Skipping SQL and operating on SQLite directly

The contest requires the data to live in SQLite, the small database inside most phones and browsers. Normally you hand SQLite a sentence in SQL. SQLite parses it, plans it, compiles it into its own bytecode, and runs that on its storage engine, a B-tree: a sorted tree of 4 KB pages where finding any row takes only a few hops from the top.

This server skips most of that. The "feed" and "get a post" reads are compiled into the same program as SQLite itself, and they call SQLite's internal B-tree functions directly.

For example, a feed needs the like count of 20 posts. Instead of 20 separate counting queries, the engine positions one cursor at the lowest post id in the "likes by post" index and walks forward once, tallying as it goes:

explore/db/engine.ctrimmed: the fast cell-walking variant is left out
// Counts likes for post ids in [lo, hi] with one likes_post_id_idx range scan.
static i64 count_likes(eng *e, i64 lo, i64 hi, u32 *counts) {
  BtCursor *c = rcur(e, C_L); if (!c) return -1;
  UnpackedRecord *r = e->uk_lpid; int res;
  r->nField = 1; r->default_rc = +1; r->eqSeen = 0; r->errCode = 0;
  r->aMem[0].flags = MEM_Int; r->aMem[0].u.i = lo;            // search key: post id lo
  if (sqlite3BtreeIndexMoveto(c, r, &res) != SQLITE_OK) return -1;
  ...
  do {
    u32 amt; const u8 *rec = idx_fetch(c, &amt); u64 t[1]; const u8 *d[1];
    if (!rec || rec_decode(rec, amt, 1, t, d) != 1 || !st_isint(t[0])) return -1;
    i64 pid = st_int(t[0], d[0]);
    if (pid > hi) break;                                          // past the last post: done
    total++; if (counts) counts[pid - lo]++;
  } while ((rc = sqlite3BtreeNext(c, 0)) == SQLITE_OK);
  return rc == SQLITE_OK || rc == SQLITE_DONE ? total : -1;
}

The feed's 20 author lookups go out as one batch: the engine sorts the keys, walks the user table once, and lets neighbouring keys share each page it fetches. It's checked against SQLite's own seek on 714,693 keys with no mismatches, and made the feed another 5–11% faster on the Xeon.

One change goes inside SQLite's own source: pcache1-maxkey, a 12-line bookkeeping fix so a commit no longer scans the whole page cache after certain B-tree changes. The bar is strict: same file format, same results, and the same results on SQLite's own test suite (about a million cases). Another entry's one-line fix for the same scan (#154) was just as fast but failed one of SQLite's savepoint tests, so this one ships.

Saving writes: one disk write per commit

SQLite in "WAL" mode appends each changed page to a log file, as two pieces: a 24-byte header and then the 4 KB page. A commit that touches 10 pages makes 20 separate write calls. The server slips a thin layer between SQLite and the disk that holds the pieces in memory and sends the whole commit as one write. It knows the commit is complete because SQLite marks the last frame's header. All of a batch's writes share one transaction (group commit), and no reply leaves until that commit returns.

explore/db/engine.cthe end of the layer's write function
  if (n == 24 && o != c->next) {                               // a header rewritten in place at commit:
    ...  flush what's buffered, then write this header straight through  ...
  }
  ...
  memcpy(c->buf + c->n, b, (size_t)n); c->n += (size_t)n;     // just remember the bytes
  if (n == 24) {                                                 // a 24-byte frame header:
    const u8 *h = b;                                             //   non-zero "db size" = commit frame
    c->commit_hdr = (h[4] | h[5] | h[6] | h[7]) != 0;
    return SQLITE_OK;
  }
  if (c->commit_hdr) { c->commit_hdr = 0; return cw_flush(c); }   // the commit frame is complete
  return SQLITE_OK;

The first branch is there because SQLite's own test suite caught a case the contest's checks never reach: SQLite sometimes rewrites a header in place just before a commit finishes, and holding that one back could lose a confirmed write in a crash. Those rewrites now go straight to disk, and the engine's crash test loses 0 of 60 commits.

Checkpoints: short and often

The log can't grow forever. Every so often SQLite copies the logged pages back into the main database file, a checkpoint, and waits for the disk. On the test box one big checkpoint can take hundreds of milliseconds, and every request in line waits too.

So the server checkpoints little and often: every 4,096 new log frames, the event loop runs SQLite's own "RESTART" checkpoint right after the batch's replies have been sent. The log stays at about 5,500 frames, the longest pause is about 100 ms, no writes are held, and it costs less CPU than the alternatives (9.9 against 12–15 µs per request locally). It's borrowed from the previous leader. The project's own re-implementation of SQLite's checkpoint on io_uring is still in the build, one flag away (DB_CKPT=uring): byte-identical, and about 28,000 simulated crashes recover, but near the limit it fell behind and stalled for up to 0.9 s.

5REPLY

The memory wall: drain, budget, and a floor

Replies are assembled in a per-batch scratch area and handed to the kernel only after the commit. The interesting part is what happens when memory runs short.

Every open connection costs the kernel memory: about 4.3 KB on the Xeon with the contest's kernel, which can't be shrunk without admin rights. On a 2 GB box that puts the wall at roughly 340,000 open connections. The server's own share is small: 32 bytes per connection, against 63 for the previous leader (Xeon, 60,000 idle connections). Three layers keep it on the right side of the wall.

1. Drain-first: a stall costs time, not memory

Because requests are copied out of the kernel as they arrive (about 0.5 KB each instead of 4 KB), a short stall turns into a little latency instead of a pile of kernel memory. Without it, one checkpoint stall at 425,000 users could queue around 100,000 requests in the kernel and run the box out of memory.

2. 503s with an error budget

When a backlog builds up while memory is short, the server answers the oldest waiting requests with an instant "503, try again": no login check, no database work, and the connection stays open. It looks only at memory and queue length, and in normal load it never fires. The budget caps it: at most 0.6% of requests, plus a one-off burst of 20,000, so the valve can never push the server past the contest's 1% error limit on its own. Once the budget is spent, requests are simply served and drain-first's buffers absorb the backlog. Uncapped, the 503 count grew with load and went over 1%; with no valve, 475,000 users ran out of memory.

3. Memory floors

Below 200 MB of available memory the server stops accepting new connections, so newcomers wait in the kernel's queue, which costs the server nothing. Below 120 MB it also closes connections that have been idle for 20 seconds or more. Both look only at memory.

The server doesn't hang up on active users to save memory: each Connection: close costs a reconnect, and at 450,000 users that meant about 80,000 reconnects per run and a worse tail. It's one flag away (CURSED_CONN_POLICY=1) if the scored box proves otherwise.

Every trick has an off switch

How cursed would you like it?

Each unusual thing the server does can be switched off when it's built, one knob at a time or all at once with a preset. All three presets pass the contest's 42 checks, so you can measure exactly what the tricks buy. The boring build doesn't just promise to stay on SQLite's public API: the build fails if the program references any SQLite function outside the public header.

Behind the scenes

How it got here

  • One person and about fifteen parallel AI coding sessions built it, each session exploring one component (parser, JWT, database, event loop…) and the winners vendored into one server.
  • Only the Xeon decides. The authors' Apple laptop misled in both directions (SQLite ran 2.7–4× slower on the Xeon, and the laptop's fast disk hid checkpoint stalls), so one session acted as a broker, queuing over 150 experiments on two rented boxes matching the contest machine.
  • The checkpoint went through four designs: inline, a background thread with a write gate, the project's own io_uring re-implementation, and finally the plain bounded one, which won near the limit.
  • Load shedding started as hanging up on people near the memory limit and ended as a 503 budget plus an accept floor, once local runs at the contest's load showed that each reconnect cost more than it saved.
  • Plenty didn't ship: two more SQLite patches, SIMD inside SQLite's page search, a bytecode JIT, and Zig and Rust ports of the components. The full story, with the evidence, is in docs/how-this-was-built.md in the source repository.

Pocket glossary

µs / ns
Microsecond (a millionth of a second) / nanosecond (a billionth).
p95, p99
The response time that 95% (or 99%) of requests beat. The contest cares about the slow tail, not the average.
kernel
The core of the operating system. It owns the network card, the disk and memory, and programs must ask it for everything.
system call
One request from a program to the kernel. Relatively expensive.
io_uring
A Linux interface where program and kernel exchange work through shared queues instead of one call per operation.
SIMD
CPU instructions that apply one operation to many values at once (AVX2: 32 bytes, AVX-512: 64 bytes).
JWT, HMAC
A signed login token, and the keyed hash used to check its signature.
B-tree
The sorted tree of pages SQLite stores tables and indexes in.
WAL, checkpoint
SQLite's append-only change log, and the step that copies it back into the main file.
