cursed-http · a guided tour

Serving a crowd from a $12 computer by doing everything the hard way

A walkthrough, for curious non-experts, of a web server built for a speed contest. It uses every trick its authors could justify, and a few they mostly built because they could.

The entry itself: pull request #158 on the challenge repo (a draft).

The game

One small box, as many users as it can carry

The $12 server challenge asks everyone to build the same tiny social network: a feed of posts, the ability to read one post, like it, and write a new one, with logins checked on every write. Everyone gets the same cheap rented machine.

Then the organizer points a crowd of simulated users at it. Each one scrolls the feed, opens a post, sometimes likes it, rarely writes one, and pauses to "read" in between. The crowd grows until the server cracks. Your score is the largest crowd the server holds for five minutes while three things stay true:

  • 95% of requests answered in under half a second,
  • 99% answered in under one second,
  • fewer than 1% of requests fail.

That's the only number that counts. Not elegance, not requests per second. Every decision on this page was judged by one question: does it let us hold more users?

In plain termsEach simulated user asks for something about once every 10 seconds. The previous winner held 264,000 users, which is about 25,000 requests a second. One core has to deal with each in roughly 40 millionths of a second (µs), on average, forever.

Where the time actually goes

You might guess the hard part is the "thinking": reading the request, checking the login, querying the database. Measured on the real Xeon, it mostly isn't. Most of each request's time is the operating system shuffling network packets.

So why make parsing 3× faster, if it was never the bottleneck? Partly because the project's brief was "maximally cursed", and partly because each nanosecond saved is free. The real wins, though, come from the parts that move the big bar: how the server talks to the kernel, how it touches the database, and how much memory each user costs. At the contest's load, both CPU and memory run out somewhere around 250,000–340,000 users by current estimates, so both matter.

The journey of a request

Follow one request through the server

The server is one program running on one thread. It never handles requests one at a time. Every time it wakes up, it grabs everything that has arrived (up to 128 requests or 2 ms of waiting) and pushes the whole batch through five stages together.

1RECEIVE

Talking to the kernel without knocking on its door

A program can't touch the network card itself. It has to ask the operating system's kernel: "anything new on connection 4,071?", "please send these bytes". Each ask is a system call. That's a trip across a security boundary, and it costs far more than ordinary code. With 300,000 connections, a classic server makes millions of those trips a second.

io_uring is a newer Linux feature that replaces the knocking with two shared mailboxes. The program drops requests into one ring ("receive on all of these", "send this"), and the kernel drops finished results into the other. One system call can hand over hundreds of jobs, and sometimes none is needed at all.

The 65,535 problem, and the multi-ring trick

The contest machine limits each program to 65,535 open files, and on Linux every network connection normally counts as a file. That would cap the server at about 65,000 users, far short of the 264,000 users the previous winner held.

io_uring has an escape hatch called direct descriptors: connections that live only inside a ring's private table and never become ordinary files. Each ring's table also tops out at 65,535, so the server simply runs several rings and adds another whenever the current ones fill up. Here's the code that asks the kernel to accept a new connection straight into a free slot of a ring's table:

explore/io/loop.craw io_uring, no helper library
static void arm_accept(loop_t *L, int ri, int multi)
{
    ring_t *r = &L->rings[ri];
    struct io_uring_sqe *s = get_sqe(L, r);      // a free slot in the submission ring
    s->opcode = IORING_OP_ACCEPT;
    s->fd = L->lfd;                              // the listening socket
    s->ioprio = multi ? IORING_ACCEPT_MULTISHOT : 0;
    s->file_index = IORING_FILE_INDEX_ALLOC;     // "put it in your own table, not in the file table"
    s->user_data = ud_mk(OP_ACCEPT, (unsigned)ri, multi ? 0 : 1, 0);
    if (multi) { r->accepting = 1; L->acc_ring = ri; }
    else r->singles++;
}

Receiving uses the same idea. Each connection keeps one standing ("multishot") receive armed, so the kernel drops every new request into a shared pool of buffers without being asked again. The team also built a leaner mode where idle connections hold only a cheap "tell me when data arrives" ticket (a multishot poll). It saves about 190 bytes per connection on this kernel, but it lost a bigger fight: when 300,000 connections closed at once, it left about 631 MB of socket buffers behind for a moment, enough to run the box out of memory. So the standing receive is the default, and the lean mode is an opt-in. The server also keeps 256 accepts in flight, because on this kernel version the fancier "accept forever" mode stalls under a flood of new connections. Lessons like that came from reading rival entries.

One more receive trick arrived in the final build: drain-first. Normally a request that arrives while the server is busy waits in the kernel's socket buffer, which costs about 4 KB of kernel memory per request. Now the server copies each request out of the kernel as soon as it arrives, into its own compact buffers at about 0.5 KB each, and works through them in order. Parsing, login checks, commit-before-reply and per-connection order are all unchanged; only where the waiting happens moves. It costs no measurable CPU at normal load on the Xeon and cut median latency by about 30% (experiment 122). Why it matters is the 425,000-user story in how it breaks, step by step.

2PARSE

Reading 64 letters in one step

A request arrives as plain text: a line like GET /posts/42 HTTP/1.1, then a few header lines such as Authorization: Bearer …, each ending in an invisible line-break. The usual way to read it is letter by letter: is this a line-break? no. This one? no…

Modern CPUs have SIMD instructions (Single Instruction, Multiple Data). One instruction loads 32 or 64 letters into a wide register and compares all of them against a line-break at once. The answer comes back as a bitmask, one bit per letter, with a 1 wherever there's a match. Finding the next line is then just "where's the next 1 bit?", which is itself a single instruction.

Try it: the line-break mask

Edit the request. Each box is one byte of the first 64. The highlighted ones are the line-breaks (\n) that a single compare finds in one go.

Here's the real version for Intel's AVX2 instructions. It loads two 32-byte chunks, compares every byte against '\n', and squeezes the results into one 64-bit mask, exactly like the demo above:

explore/parser/http.halso has AVX-512, ARM NEON and plain-C versions
FP_INLINE uint64_t fp_lf64_simd(const char *p) {
  const __m256i LF = _mm256_set1_epi8('\n');                     // 32 copies of '\n'
  __m256i v0 = _mm256_loadu_si256((const void *)p),               // bytes 0..31
          v1 = _mm256_loadu_si256((const void *)(p + 32));        // bytes 32..63
  return fp_mm2(_mm256_cmpeq_epi8(v0, LF), _mm256_cmpeq_epi8(v1, LF));   // 64 compares -> 64 bits
}

There's a second twist: the parser isn't hand-written. A script generates it from the API's own specification, so it knows the handful of request shapes this API can receive and recognises each from its first few bytes. Anything unusual (an old HTTP version, odd headers) falls back to a slower general-purpose parser. That one is SIMD too, and it gives identical answers to the well-known picohttpparser on every input the team could throw at it.

Result on the Xeon: 37 nanoseconds per request, against 107 for picohttpparser with the same routing on top.

The really cursed bit: parsing different people's requests side by side

SIMD normally speeds up one long piece of text. But each request is short, and a batch holds dozens of them from different users. So the "lane-parallel" parser turns the problem sideways: it puts one request from each of 4 or 8 connections into the lanes of a single register, and parses them all with the same instructions.

explore/batch-parse/bp.hthe whole contract in two lines
const char *buf[n]; int len[n];  req_t out[n]; int ret[n];
bp_parse(n, buf, len, out, ret);    // ret[i] = fast_parse(buf[i], len[i], &out[i]), any n >= 0

Every lane must return exactly what the one-at-a-time parser returns. A test build checks that live: 165,004 real requests compared lane by lane, with zero mismatches.

3LOG-IN CHECK

Checking eight signatures with one set of instructions

Liking a post or writing one requires a login token, a JWT. It's a short string that says "this is user 1234, valid until Tuesday", followed by a cryptographic signature. To check it, the server recomputes the signature with a secret key (a calculation called HMAC-SHA256) and compares. The rules forbid caching the answer: every request's token is checked from scratch.

SHA-256 is 64 rounds of adding, rotating and mixing 32-bit numbers. One message can't be split across lanes, because each round needs the previous one. But eight different messages can each take a lane. That's multi-buffer hashing: the server gathers every token in the batch and runs them through the rounds side by side, one token per 32-bit lane of an AVX-512 register.

Below is one SHA-256 round. V is "a vector of 8 numbers", so every VADD or VROR is one instruction doing eight lanes' worth of work. The identical source becomes the plain-C version when V is just a single number.

explore/jwt/jwt_mb.incone round, for every lane at once
#define MB_RND(a, b, c, d, e, f, g, h, t, wt)                                    \
    do {                                                                         \
        V t1 = VADD(VADD(VADD(h, VXOR3(VROR(e, 6), VROR(e, 11), VROR(e, 25))),   \
                         VADD(VCH(e, f, g), VSET1(K256[t]))), (wt));             \
        V t2 = VADD(VXOR3(VROR(a, 2), VROR(a, 13), VROR(a, 22)), VMAJ(a, b, c)); \
        d = VADD(d, t1);                                                         \
        h = VADD(t1, t2);                                                        \
    } while (0)

A practical detail: this Xeon slows its clock when code uses the full 512-bit registers heavily, so the shipped version uses AVX-512's new instructions on 256-bit registers instead. The 512-bit variant was measured, and rejected.

On the Xeon, with a typical batch of three tokens: 608 ns per token, against 6,201 ns for the C++ library jwt-cpp and 8,739 ns for Go's popular golang-jwt.

4DATABASE

Skipping SQL and operating on SQLite directly

The contest requires the data to live in SQLite, the small database inside most phones and browsers. Normally you hand SQLite a sentence in the SQL language. SQLite parses it, plans how to run it, compiles it into its own little bytecode, and runs that on its storage engine, a B-tree: a sorted tree of 4 KB pages where finding any row takes only a few hops from the top.

This server skips most of that. The "feed" and "get a post" reads are compiled into the same program as SQLite itself, and they call SQLite's internal B-tree functions directly.

For example, a feed needs the like count of 20 posts. Instead of 20 separate counting queries, the engine positions one cursor at the lowest post id in the "likes by post" index and walks forward once, tallying as it goes:

explore/db/engine.ctrimmed: the fast cell-walking variant is left out
// Counts likes for post ids in [lo, hi] with one likes_post_id_idx range scan.
static i64 count_likes(eng *e, i64 lo, i64 hi, u32 *counts) {
  BtCursor *c = rcur(e, C_L); if (!c) return -1;
  UnpackedRecord *r = e->uk_lpid; int res;
  r->nField = 1; r->default_rc = +1; r->eqSeen = 0; r->errCode = 0;
  r->aMem[0].flags = MEM_Int; r->aMem[0].u.i = lo;            // search key: post id lo
  if (sqlite3BtreeIndexMoveto(c, r, &res) != SQLITE_OK) return -1;
  ...
  do {
    u32 amt; const u8 *rec = idx_fetch(c, &amt); u64 t[1]; const u8 *d[1];
    if (!rec || rec_decode(rec, amt, 1, t, d) != 1 || !st_isint(t[0])) return -1;
    i64 pid = st_int(t[0], d[0]);
    if (pid > hi) break;                                          // past the last post: done
    total++; if (counts) counts[pid - lo]++;
  } while ((rc = sqlite3BtreeNext(c, 0)) == SQLITE_OK);
  return rc == SQLITE_OK || rc == SQLITE_DONE ? total : -1;
}

The feed's other job is finding the 20 posts' authors. Those lookups go out as one batch: the engine sorts the 20 keys, walks the user table once, and lets neighbouring keys share each page it fetches. Inside a page it guesses where a row id sits, because ids are dense, rather than halving the range every time. It's checked against SQLite's own seek on 714,693 keys with no mismatches, and it made the whole feed another 5–11% faster on the Xeon (experiment 53).

Then: patching SQLite itself (four tried, one ships)

The team also tried changes inside SQLite's own source. The bar for keeping one was strict: faster on the real Xeon, the same file format, query results and bytes on disk as stock SQLite, and the same results on SQLite's own test suite. Three patches got as far as the Xeon. Only one survived to the end, and the other two are good examples of why measuring matters.

The first one: when you look up row 1,209 right after row 1,208, they're almost certainly on the same leaf page, yet stock SQLite climbs back to the root of the tree every time. The btree-sameleaf patch checks the leaf first.

explore/sqlite-patches/patches/btree-sameleaf.patchthe core of a 46-line patch to sqlite3.c (since removed)
+  /* If the cursor is on a leaf whose rowids span intKey, the row (if any)
+  ** is on this leaf: search it without going back to the root. */
+  if( pCur->eState==CURSOR_VALID
+   && pCur->iPage>0
+   && pCur->pPage->leaf
+   && pCur->pPage->isInit
+   && pCur->pPage->nCell>1
+  ){
       ...  compare intKey with the first and last cell's rowid  ...
+        goto moveto_table_search_page;
+  }
   rc = moveToRoot(pCur);

The second, btree-interp, searches a page the way you'd look up a word in a dictionary (row 1,209 on a page of rows 1,101–1,250 is probably about 70% of the way in), rather than always halving. It was faster on the Xeon, but it failed one of SQLite's own tests: on a deliberately corrupted page with duplicate row ids, it found a different duplicate than stock SQLite does. Valid databases are unaffected, but "identical to stock" is the bar, so it was removed too. The one that ships, pcache1-maxkey, is a 12-line bookkeeping fix: after certain B-tree changes, a commit no longer scans the whole of SQLite's page cache. Other ideas didn't survive either: putting SIMD inside SQLite's page search lost on the Xeon, so it was dropped.

The fourth was borrowed. Another entry in the contest (pull request #154) spotted the same page-cache scan that pcache1-maxkey fixes, and fixed it from the other end with a clever one-line change to SQLite's page balancing: a different temporary page number. It was just as fast, and it passed the team's own checks on the contest database. SQLite's own test suite failed it, though: in one savepoint test, on databases using a feature called incremental auto-vacuum, the temporary page could be one SQLite was still holding, and that page's contents got thrown away. The contest database doesn't use auto-vacuum, so it never bites there. But the team kept its own patch, which passes everything, and credits #154 for the diagnosis in its submission. The lesson they wrote down: a test only proves things for the situations it actually exercises.

Saving writes: one disk write per commit

SQLite in "WAL" mode appends each changed page to a log file. It writes each page as two pieces, a 24-byte header and then the 4 KB page, so a commit that touches 10 pages makes 20 separate write calls. The server slips a thin layer between SQLite and the disk that holds the pieces in memory and sends the whole commit as one write. It knows the commit is complete because SQLite marks the last frame's header.

explore/db/engine.cthe end of the shim's write function
  if (n == 24 && o != c->next) {                               // a header rewritten in place at commit:
    ...  flush what's buffered, then write this header straight through  ...  // (the fix, see below)
  }
  ...
  memcpy(c->buf + c->n, b, (size_t)n); c->n += (size_t)n;     // just remember the bytes
  if (n == 24) {                                                 // a 24-byte frame header:
    const u8 *h = b;                                             //   non-zero "db size" = commit frame
    c->commit_hdr = (h[4] | h[5] | h[6] | h[7]) != 0;
    return SQLITE_OK;
  }
  if (c->commit_hdr) { c->commit_hdr = 0; return cw_flush(c); }   // the commit frame is complete
  return SQLITE_OK;

SQLite's own test suite found a real bug here, and it's the kind the contest's durability rule exists for. Occasionally SQLite goes back and rewrites a few log headers in place just before a commit finishes (when a big transaction had to write a page out early and then changed it again). The shim held on to the last of those rewrites, the one carrying the commit's final checksum, and the commit returned with it still in memory. A crash at that moment would have lost a write the server had already confirmed. A crash test reproduced it (39 of 40 such commits lost). Now any header rewrite goes straight to disk, and a guard after every commit flushes anything left over and fails the batch if that flush fails. The same test now loses none. The contest's own checks never trigger this path, which is exactly why the team ran SQLite's.

Checkpoints: three designs, and the boring one won

The log file can't grow forever. Every so often SQLite copies the logged pages back into the main database file, a checkpoint, and then waits for the disk to confirm. On the test box that wait takes 130–270 ms, and if it happens in the middle of serving, every request in line waits too. That spike was the single biggest threat to the "99% under 1 second" rule.

The first fix moved the checkpoint off the request path and added a gate: SQLite's own checkpoint ran on a second thread, and when the log reached its high mark the server kept answering reads but left new writes waiting, unread, in the network buffers until the checkpoint caught up (typically tens of milliseconds).

The second design is probably the most cursed thing in the project: the team re-implemented SQLite's checkpoint step itself, as a little state machine on the same io_uring rings that serve the network. It takes the same steps in the same order as SQLite (sync the log, copy each page's latest version into the database file, sync the database, mark the log as copied) and produces the same file. Only the waiting changes: the disk work goes out as io_uring operations between batches instead of blocking calls. It's tested byte-identical against SQLite's own checkpoint, and about 28,000 simulated crashes and power cuts all recovered cleanly. At moderate load on the Xeon it matched the thread (experiments 50 and 51). It's still in the build, one flag away (DB_CKPT=uring).

But the design that ships is the plain one, borrowed from the previous leader. Every 4,096 new log frames, the event loop runs SQLite's own "RESTART" checkpoint right after the batch's replies have been sent, so the log never grows big and is reused in place. There's no gate and no writes are held. In the arena near the limit, the io_uring version could fall behind and stall for 432–861 ms at a time (once 9 seconds). The bounded checkpoint kept the log at about 5,500 frames, its longest pause at 31–103 ms, and it even cost less CPU (9.9 against 12–15 µs per request locally). The "lawful" build uses SQLite's own checkpoint run right after each batch's replies, and the "boring" build leaves it to SQLite's automatic checkpoints.

Checkpoints also had a memory cost. With the gate design the log could grow to about 256 MB, and the kernel kept all of it cached in memory that the connections needed. The team first fixed that by telling the kernel to forget each log page once copied (posix_fadvise), which cut it to 15–18 MB on the Xeon (experiments 39 and 40). The bounded checkpoint makes the problem smaller still, because the log itself stays at about 5,500 frames. Testing also caught a real bug along the way: under write-heavy load the old gate never closed, so the log just kept growing. It was fixed, before the gate was retired.

One more batch-level trick is allowed outright by the rules: group commit. All of a batch's writes share one transaction and one commit, and every reply in the batch waits for it.

5REPLY

The memory wall, and a valve with a budget

Replies are assembled in a per-batch scratch area and handed to the kernel only after the commit. The interesting part is what happens when memory runs short.

CPU is one wall; memory is the other. Every open connection costs the kernel about 4.3 KB, measured on the Xeon, and that can't be shrunk without admin rights. The box has about 1,630 MB free. After leaving room for the server itself and its database cache, it runs out somewhere around 340,000 idle connections. Past that, keeping one connection per user is impossible.

The first plan for getting past the wall came from reading the organizer's load generator. Simulated users spend most of their time "reading", time spent reconnecting isn't counted as delay, and a user whose connection was closed simply opens a new one next time. So near the memory limit, the server would attach Connection: close to a fraction of replies, idle users would share fewer open connections, and the server could carry more users than it has sockets. It works, and it's still in the build. But it ships switched off, for reasons that come next.

Play with it: users vs. the memory wall

This is the switched-off plan, to show what hanging up would buy in memory. A rough model: 4.3 KB of kernel memory per open connection, against the ~1,430 MB left of the box's 1,630 MB once about 200 MB is set aside for the server and its database cache. With shedding, the small Xeon test settled at 2.75 users per open connection. That test used 5,000 users, so treat the shedding line as an illustration. The model ignores CPU, which at the contest's load may run out first.

Everyone keeps a connection open
With "Connection: close" shedding

Hanging up isn't free. Each reconnect costs the server about 8–9 µs of extra CPU on the Xeon (experiment 18), and at the contest's load CPU is the scarcer resource. The rule for when to hang up went through two versions. The first counted connections, and shed once they reached 95% of a memory-derived cap; in the arena it hung up on people while memory was still plentiful and failed at 375,000 and 400,000 users. The second only reacted to memory (nothing shed above 400 MB free, up to half of replies by 200 MB), and passed both on the same build. But at 450,000 users even that version made about 80,000 users reconnect per run, and the slowest requests got slower. So by default the server no longer hangs up at all (CURSED_CONN_POLICY=1 brings it back if the contest box proves otherwise). For the record, this is the weighted coin flip it uses when switched on:

explore/io/loop.cthe hang-up coin flip, off by default
int loop_close_hint(loop_t *L, loop_conn id)
{
    (void)id;                                   // never aimed at a particular client
    float f = L->st.close_frac;
    if (f <= 0) return 0;                       // plenty of memory: keep everyone
    L->rng ^= L->rng << 13; L->rng ^= L->rng >> 17; L->rng ^= L->rng << 5;   // xorshift
    if ((float)(L->rng >> 8) < f * 16777216.0f) { L->st.hint_closes++; return 1; }
    return 0;
}

The server's own memory is small next to the kernel's: 32 bytes per connection in the program itself, against 63 for the previous leader, measured side by side on the Xeon with 60,000 idle connections (experiment 37). That works out to roughly 100 MB less at 340,000 connections, room for about 23,000 more. In the local load-test arena at 50,000 users (under a lighter load than the contest uses), where both servers passed, the whole server peaked at 229 MB against the leader's 255 MB, measured with the lean receive mode that's now an opt-in. That's laptop Docker, not the Xeon, but it's the same direction. Below the valves there are emergency floors as a last resort: under 100 MB free it stops accepting new connections, and under 60 MB it gently closes connections that have been idle for 20 seconds. That beats letting the system's out-of-memory killer end every connection at once.

One more emergency valve exists but is switched off: deadline shedding. When on, any request that has waited too long in the kernel's queue gets an instant "overloaded" reply instead of a slow one, turning would-be tail latency into a few fast errors inside the contest's 1% error allowance. It looks only at how long the request waited, never at who sent it or what it asks for. In the arena at 350,000 users it turned 35% of requests into errors and still failed on latency, so it stays off.

That leaves one memory valve, and it's on: 503s with a budget. When a backlog of waiting requests builds up while memory is short, the server answers the oldest of them with an instant "503, try again", with no login check and no database work, and keeps the connection open. It looks only at memory and queue length, and in normal load it never fires: in the Xeon test at 10,000 users it stayed idle (experiment 141). The twist is the budget. At most 0.6% of requests may get a 503, plus a one-off burst of 20,000; once the budget is spent, requests are simply served, and drain-first's buffers absorb the backlog. Without a cap, the valve's 503 count grew with load and went over the contest's 1% error limit in four of five runs at 450,000 users on a busier laptop. With no valve at all, 475,000 users ran out of memory. With the cap, the runs at 450,000 and 475,000 sent 11,800–20,500 503s each, 0.19–0.30% of requests (laptop Docker, 1-minute holds).

The memory accounting itself was a small investigation. The usual "free memory" figure turned out to overstate headroom by about 1 KB per connection, because some kernel memory looks reclaimable but stays pinned while the socket is open. The server now measures available memory minus that "reclaimable" slice, and its memory valves read that figure.

★BEHIND THE SCENES

A queue for the one machine whose opinion counts

All of this was written on an Apple laptop, a different kind of chip entirely. It can't run AVX-512 at all, and it turned out to be misleading in both directions: SQLite paths ran 2.7–4× slower on the Xeon, and the laptop's fast disk hid the checkpoint stall completely. So the rule became: only the Xeon decides.

The team rented two machines matching the contest box (same Xeon Platinum 8260, same 1 core and 2 GB, same Linux kernel). About fifteen AI coding sessions were working on different parts in parallel, but none of them logs in to the boxes. Instead, one session acts as a broker:

a payload's manifest.jsonshape from synteq-experiments/README.md
{"requester_session_id": "local_…",
 "title": "checkpoint thread + write gate, round 2",
 "reasoning": "measures batch p99 with the gate vs inline checkpoints; decides the checkpoint design, which sets the tail latency that fails runs",
 "timeout_s": 180, "needs_root": false}

The broker also ran known entries, a C++ server and the previous contest leader (written in Rust), on the same boxes as rulers. That's how the team knows how its numbers relate to the organizer's machine. Under the same load, this server used 32.2 µs of CPU per request against the leader's 37.6 µs.

Every trick has an off switch

How cursed would you like it?

Each unusual thing the server does can be switched off when it's built, one knob at a time, or all at once with CURSED=boring. The boring build is by-the-book: stock SQLite, ordinary SQL queries, SQLite's own file layer and checkpoints, plain one-at-a-time login checks, and the standard picohttpparser for every request. Both builds pass the contest's 42 checks, so you can measure exactly what each trick buys. A middle setting, CURSED=lawful, uses completely stock SQLite through its public API but keeps every trick outside the database.

On the Xeon, at the contest's real load (10,000 simulated users, loopback), the builds used this much CPU per request: max 29 µs at the PR's current commit (experiment 141), and lawful 43 µs, boring 47 µs at an earlier commit (experiments 66–67; the later changes don't touch those builds). All three pass the contest's 42 checks on the Xeon. So the curses, taken together, save about 40% of the CPU per request, and the SQLite curses account for most of that. Most of the gap is the feed: 8.2 µs through SQLite's cursors against 23.2 µs through the spec's SQL (Xeon, experiment 15).

The fallback parser is swappable too: our SIMD one, picohttpparser, Node's llhttp, uWebSockets (C++), hparse (Zig) or httparse (Rust). All 24 combinations of fast and fallback parser pass the 42 checks. With every SQLite knob combined, 52 database configurations pass with the database's integrity check clean (Linux, in Docker). The server prints the mode it was built with when it starts.

The boring build doesn't just promise to stay on SQLite's public API; it's checked. The build lists every SQLite function the program references and fails if any of them isn't in SQLite's public header. The public-API engine and the cursed one gave byte-identical responses to 3,408 test requests.

The local arena runs the organizer's load generator against each server, boxed into one CPU, 2 GB and no swap on a laptop, at the contest's real load. On this rig ours holds 475,000 users (two runs out of two) and the previous leader holds 400,000; it's killed for running out of memory at 425,000. At 400,000 ours answers its slowest 1% of requests in 20 ms against the leader's 679 ms, about a thirty-fourth, with about 155 MB less memory and 9.3 µs of CPU per request. Three changes got it there: drain-first receiving, the bounded checkpoint, and 503s with a budget instead of hanging up. That's local arm64 with 1-minute holds, not an organizer score.

One caveat carries over to the real machine. On the Xeon with the contest's kernel, each open connection costs about 4.3 KB of kernel memory, which puts the wall at roughly 340,000 connections on a 2 GB box. Past that the server has to hold users by asking some to reconnect, which costs CPU, so the laptop's 350,000 isn't guaranteed there. A correction along the way: the arena's first user counts used a lighter load, with users pausing 2.5 times longer between requests. Those were withdrawn and re-run, and the numbers above are from the re-run.

Two side studies keep the headline honest. First, the gap is not all cleverness: the previous leader, given just one of this project's ideas (checkpointing on a background thread, or turning off its 1 GB memory map of the database), held 450,000 users on the same rig (explore/rust-port). Second, a profile of the PR build found that most of each request's CPU is the kernel's own network path, about 6 µs locally and 13 µs on the Xeon, which no change in the server's own code can remove (explore/hotspots).

Turning up the crowd

How it breaks, step by step

A server doesn't fail all at once. Here is what happens inside this one as the crowd grows, rung by rung, from the local arena at the contest's load. Every number is local arm64 with 1-minute holds: the server boxed into one CPU and 2 GB on a laptop, with the organizer's load generator next to it. Up to 300,000 users the numbers come from a build from before the freeze, 350,000 and 375,000 from earlier builds, and 400,000 to 475,000 from the exact build in the PR.

  1. 200,000–300,000 USERSEveryone keeps their connection

    Server
    Nothing is ever closed. Each request costs 12–15 µs of CPU, and the event loop is busy only 22–40% of the time.
    Kernel and memory
    Almost all the memory is the kernel's bookkeeping for open connections: 745 MB at 200,000 users and 1,116 MB at 300,000. The server program itself stays around 30–34 MB.
    Users see
    The slowest 1% of requests take 4–7 ms. No errors.

  2. 350,000–400,000 USERSStill nothing closed: memory has room

    Server
    All 400,000 connections stay open, and with plenty of memory still free, neither memory valve has anything to do. Each request costs about 10–13 µs of CPU.
    Kernel and memory
    1,302 MB of kernel memory at 350,000 users and 1,488 MB at 400,000, with 1,593 MB in total at the peak on the PR's build.
    Users see
    p99 116 ms at 350,000 and 20 ms at 400,000 on the PR's build, no errors: both pass. The older rule, which shed by connection count once open connections reached 95% of a 380,000 cap, started hanging up here. On the same test build it made 3,100–5,100 users a second reconnect, pushed CPU to 84–90%, and failed at both 375,000 (p99 2.1 s) and 400,000 (7.2 s). That's why a memory-based rule replaced it, before hanging up was switched off altogether.

  3. 425,000 USERSA traffic jam in the kernel, defused

    Server
    Earlier builds hit a jam here: near the end of the ramp a long database checkpoint stalled the event loop, and around 100,000 requests piled up in the kernel's socket buffers at about 4 KB each until the box ran out of memory (a classic case of bufferbloat). Two changes defused it. Drain-first copies arriving requests out of the kernel at about 0.5 KB each, and the bounded checkpoint keeps every pause short, at most about 100 ms.
    Kernel and memory
    Kernel memory for the connections is about 1.58 GB, almost nothing waits in socket buffers, and peak memory was 1,712 MB. CPU sat at about 43%. Nothing was shed and the 503 valve never fired.
    Users see
    p99 29 ms with no errors: a pass. The previous leader is killed for running out of memory at this size.

  4. 450,000 USERSThe budgeted valve starts working

    Server
    Memory is now short enough for the 503 valve to answer the oldest waiting requests: 11,768–15,481 of them per run, all within its one-off burst of 20,000. No connection is closed. Each request costs about 10 µs of CPU.
    Kernel and memory
    The connections take about 1.67 GB of kernel memory, and the peak was 1,829–1,844 MB of the 2 GB.
    Users see
    Both runs pass, with p99 73–115 ms and 0.19–0.24% errors, all of them fast 503s. Getting here took two detours. With hanging up switched on, this load passed three runs of three but made about 80,000 users reconnect per run. With the 503 valve uncapped, it went over the 1% error limit in four runs of five on a busier laptop.

  5. 475,000 USERSThe edge

    Server
    The valve spends its whole burst (20,203–20,460 503s per run) and then serves everything; drain-first's buffers soak up the rest of the backlog. CPU sits around 49–52%.
    Kernel and memory
    The connections take about 1.77 GB of kernel memory, and the peak was 1,955–1,961 MB: only about 85 MB under the 2 GB limit. With no valve at all, this load ran out of memory.
    Users see
    Both runs pass, with p99 159–234 ms and 0.29–0.30% errors. With so little memory left, this is the edge; nothing larger has been run on this build.

  6. ON THE REAL XEONA different wall comes first

    Server
    The contest machine has the same 2 GB but a different kernel, and there each open connection costs about 4.3 KB of kernel memory (experiment 19). That puts the wall at roughly 340,000 open connections, so free memory runs low sooner than on the laptop. The shipped build doesn't hang up to get past it, because each reconnect costs more than it saves; CURSED_CONN_POLICY=1 brings hanging up back if the contest box proves otherwise.
    Kernel and memory
    That kernel limits socket memory to about 175 MB, but the arena re-run with the same limits shows the cap alone doesn't stop a queue surge from running the box out of memory. Each reconnect costs CPU (about 8–9 µs on the Xeon, experiment 18).
    Users see
    Not measured at full scale: the 1-CPU test boxes can't generate that much load against themselves. The laptop's 475,000 is not guaranteed there.

Pocket glossary

µs / ns
Microsecond (a millionth of a second) / nanosecond (a billionth).
p95, p99
The response time that 95% (or 99%) of requests beat. The contest cares about the slow tail, not the average.
kernel
The core of the operating system. It owns the network card, the disk and memory, and programs must ask it for everything.
system call
One request from a program to the kernel. Relatively expensive.
io_uring
A Linux interface where program and kernel exchange work through shared queues instead of one call per operation.
SIMD
CPU instructions that apply one operation to many values at once (AVX2: 32 bytes, AVX-512: 64 bytes).
JWT, HMAC
A signed login token, and the keyed hash used to check its signature.
B-tree
The sorted tree of pages SQLite stores tables and indexes in.
WAL, checkpoint
SQLite's append-only change log, and the step that copies it back into the main file.
